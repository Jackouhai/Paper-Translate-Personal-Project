## Objective

Measure the online serving behavior of TranslateGemma in the PP-DocLayout
translation workflow and select a safe concurrency limit for one vLLM server.
The benchmark measures API performance only. It does not evaluate translation
quality, PDF parsing, HTML rendering, or PDF export.

## Workload

The dataset was generated by
[`scripts/build_translation_benchmark_dataset.py`](../scripts/build_translation_benchmark_dataset.py)
from actual PP-DocLayout parse outputs. It applies the same translation policy,
source-text preparation, TranslateGemma `<<<custom>>>` prompt, and per-block
generation limit as `GemmaTranslator`.

| Dataset property | Value |
|---|---:|
| Requests | 100 |
| Total input tokens | 21,014 |
| Mean input tokens/request | 210.1 |
| Total generated tokens | 12,541-12,583, depending on run |
| Mean generated tokens/request | about 125.6 |
| Source projects | `2210.17323v2` (91 blocks), `2306.00978v6-e760e338` (9 blocks) |
| Block labels | `text`: 68, `figure_title`: 30, `abstract`: 2 |
| Title translation | Disabled |

The request contents were real English academic blocks. The benchmark used
`--dataset-name custom`, the OpenAI-compatible completion endpoint, and did
**not** use `--skip-chat-template`; vLLM therefore applies the model's chat
template to the valid `<<<custom>>>` user content. `--ignore-eos` was not used,
so each response stops naturally as in the pipeline.

## Procedure

For each concurrency level, the same 100-record JSONL dataset was sent to a
server already loaded in GPU memory. The request rate was unlimited and the
client used `temperature=0`. Each listed configuration was run once.

```bash
cd services/llm-server
UV_CACHE_DIR="$PWD/.uv-cache" uv run --no-sync vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8001 \
  --endpoint /v1/completions \
  --model Infomaniak-AI/vllm-translategemma-4b-it \
  --dataset-name custom \
  --dataset-path ../../bench_data/translation_blocks.jsonl \
  --no-oversample \
  --num-prompts 100 \
  --max-concurrency <C> \
  --num-warmups 3 \
  --temperature 0 \
  --save-result --save-detailed \
  --result-dir ../../logs/vllm-bench-real
```

## Results

All 100 requests completed successfully at every tested level.

| Concurrency | Duration (s) | Request throughput (req/s) | Output throughput (tok/s) | Mean TTFT (ms) | P99 TTFT (ms) | Mean TPOT (ms) | P99 TPOT (ms) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 226.0 | 0.44 | 55.55 | 189.67 | 3,103.27 | 16.62 | 21.85 |
| 2 | 103.95 | 0.96 | 120.65 | 54.73 | 68.86 | 16.17 | 16.35 |
| 3 | 95.46 | 1.05 | 131.55 | 601.31 | 4,395.75 | 17.93 | 39.25 |
| 4 | 59.74 | 1.67 | **210.11** | 109.29 | **875.70** | 17.54 | 31.42 |
| 6 | 54.29 | 1.84 | 231.77 | 583.56 | 4,003.23 | 22.38 | 75.73 |
| 8 | 54.07 | 1.85 | 232.41 | 1,500.76 | 4,401.87 | 23.55 | 79.66 |

TTFT is time to first token. TPOT is time per generated token after the first
token. Lower latency is better; higher throughput is better.

## Interpretation

Concurrency 4 is the selected operating point.

- Compared with concurrency 2, output throughput rises from 120.65 to 210.11
  token/s, an increase of 74.2%.
- Its P99 TTFT remains below one second (875.70 ms), which is acceptable for
  an interactive PDF translation demonstration.
- Increasing from 4 to 6 adds only 10.3% output throughput, while P99 TTFT
  rises from 0.88 s to 4.00 s and P99 TPOT more than doubles.
- Concurrency 8 provides no material throughput gain over 6 but further raises
  first-token and per-token latency.

The c=1 and c=3 measurements contain long-tail TTFT outliers. They are retained
for transparency; the choice is based on the throughput-latency trade-off across
the complete sweep rather than on a single median value.

## Selected Configuration

The pipeline and standard Docker demo profile use a maximum of four in-flight
translation requests per TranslateGemma server:

```env
PPDOCLAYOUT_MAX_CONCURRENT_REQUESTS=4
WEB_DEMO_MAX_CONCURRENT_REQUESTS=4
```

The Compose demo therefore uses one translation worker and four requests per
job. If these values are changed, their product should remain at or below four;
otherwise the measured latency guarantees do not apply.

## Limitations and Reproducibility

- Each concurrency level was executed once. Repeating c=2 and c=4 at least
  three times and reporting mean plus dispersion would strengthen a final paper.
- The dataset represents 100 blocks from two parsed papers, not every paper
  category or the maximum supported context length.
- Natural EOS was used. This is representative of normal translation but is not
  a worst-case fixed-length decode test.
- GPU peak memory was not sampled during this run; only successful completion
  and serving latency/throughput were evaluated.
- Raw benchmark JSON is a local ignored artifact and is not included in the
  submission. The table above is the summary derived from those results.
